# 如何理解、展示并写进简历

这份项目已经有实际数据、可执行 SQL 和验证结果。你最需要掌握的是查询为什么这样写，以及每个结果的口径。下面的路径以最终产出为例，不要求先学完所有 SQL 语法。

## 先打开项目

项目目录名：`olist-sql-analytics`，位于你的工作区中。

在 PowerShell 进入目录，运行：

```powershell
.\run.ps1 -Serve
```

打开 `http://127.0.0.1:8765`，选择“SQL 实验台”。选一个查询，阅读注释，点击“运行查询”。服务器在当前 PowerShell 前台运行；按 Ctrl+C 关闭。

只看成果时，可以直接打开 `docs/index.html`。完整重新构建运行 `.\run.ps1`。单独执行查询运行：

```powershell
.\run.ps1 -Query -SqlFile 'sql/analysis/10_join_fanout_demo.sql'
```

本机使用 PGlite 的 PostgreSQL 引擎，不需要安装数据库服务。用 DBeaver 时，需要另有标准 PostgreSQL 服务，先用 `sql/load_postgres.psql` 导入新数据库，再连接。不能把 PGlite 文件直接当作 PostgreSQL 服务地址。

## 面试中最值得讲的三件事

**第一，解决 JOIN fanout。** 一个订单可能有多个商品、多笔支付和多条评价。直接连接会产生组合行；INNER JOIN 也会删掉缺少记录的订单。我的设计把金额先按 order_id 汇总，再选最新评价，最后连接订单事实表。2018 年 1 月错误 JOIN 的金额偏高 3.40%，正确汇总与商品源表完全对账。

**第二，明确 NULL 和分母。** 已交付不代表有完整配送日期。有 8 笔已交付订单缺少实际交付时间，它们仍在数据库中，但不参与延迟率。低评分比例只对有评价的订单计算，同时展示评价覆盖率。

**第三，保留可验证的性能证据。** 对同一天的订单查询，先比较日期类型转换和半开时间范围，再创建 purchased_at 索引。记录实际执行计划与三次预热后测量，确认所有版本返回同样的 307 笔订单。索引后的计划使用位图索引扫描；本机 WASM 耗时不能直接代表生产环境。

## 常见追问

**为什么不用 customer_id 分析复购？**
它是订单关联的客户记录 ID；customer_unique_id 才是跨订单识别客户的字段。我们用后者按窗口汇总已交付订单。

**为什么 review_id 不是主键？**
真实源文件有重复 review_id。原始每行都保留，用 source_row 标识；订单级指标用 ROW_NUMBER 选一条最新记录。相同时间的记录采用确定性的排序回退规则，文件行号不代表真实业务时间。

**为什么使用 LEFT JOIN？**
订单主表要保留缺少明细或评价的记录。LEFT JOIN 让缺失暴露出来；对金额没有匹配时 COALESCE 为 0，但同时保留 item_count/payment_count，区分“没有记录”和“真实金额为零”。

**为什么不用 FLOAT 保存金额？**
金额按源文件两位小数保留为 NUMERIC，避免二进制浮点误差影响对账。

**如何定义延迟？**
订单状态为 delivered，实际配送时间不早于购买时间，预计时间存在；比较实际交付日和预计交付日。预计字段是午夜日期，直接比较完整时间戳会把预计当天到货误判为延迟。

**延迟导致差评了吗？**
我们观察到关联，尚未做因果识别。需要控制地区、品类、卖家、季节，或设计实验与其他可靠验证，才讨论因果。

**为什么 cohort 后面有的单元格缺失？**
观察期只到 2018 年 8 月。后入组客户还没有完整后续月份，未观察月份必须留空，不能填成零。SQL 用 GENERATE_SERIES 生成可观察网格，并把网格内的零购买填零。

**Materialized view 和 view 有什么区别？**
物化视图保存结果，加快重复分析但需要刷新；普通视图保存查询定义。这个静态数据项目构建一次事实表；若 core 更新，需要 REFRESH MATERIALIZED VIEW，并重新运行验证。

## 两分钟英文介绍

> I built a PostgreSQL analysis project using Olist's public e-commerce data, covering about 99,000 orders across eight source tables. The main technical challenge was avoiding double counting when joining order items, payments and reviews. I aggregated each child table to order grain and selected one latest review per order, then validated the resulting totals against the source.
>
> The analysis covers monthly growth, category contribution, delivery performance, seller diagnostics and observed repeat purchasing. I found a strong association between late delivery and low review scores, while keeping the conclusion observational. I also measured date-filter query plans before and after adding an index. The project includes runnable SQL, automated validation, exported results and a local read-only SQL lab.
